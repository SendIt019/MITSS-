# MITSS

An input/output harness for language-model scheduling runs.

MITSS does not schedule anything and does not call any model. You feed it a
plan, it builds a prompt packet, you hand that packet to a model, you paste the
reply back, and MITSS decides whether the answer is actually legal — then
records the whole exchange so runs can be compared over time.

The point is that model output gets **checked**, not trusted.

## Requirements

Python 3.9 or newer. Nothing else. No dependencies to install, no virtual
environment needed, no network access, no credentials or tokens anywhere.

## The cycle

```bash
python -m mitss new my-session     # write a starter plan into inputs/
# edit inputs/my-session.json
python -m mitss check              # validate the plan without staging
python -m mitss stage              # create a run, build the prompt packet
```

Staging creates `runs/<timestamp>-<session>/` containing `plan.json`,
`packet.md`, and an empty `output.raw.md`.

Send `packet.md` to the model. Paste its entire reply into `output.raw.md` —
surrounding prose is fine, the fenced JSON block is what gets parsed. Then:

```bash
python -m mitss ingest             # parse, validate, constraint-check
python -m mitss report             # table, timeline, summary
python -m mitss diff RUN_A RUN_B   # compare two runs of the same plan
python -m mitss log                # append-only run history
python -m mitss status             # where things stand
```

Most commands take a run id, a unique prefix of one, or nothing at all (which
means the latest run).

Exit codes: `0` clean, `1` problems found, `2` usage error. That makes the
harness safe to drive from a script.

## Input format

A plan is one JSON file. `inputs/example-001.json` is generated by
`mitss new` and shows the full shape.

```json
{
  "session": "example-001",
  "horizon": {"start": "2026-08-11T08:00:00", "end": "2026-08-11T18:00:00"},
  "granularity_minutes": 15,
  "objectives": ["finish as early as possible"],
  "resources": [
    {"id": "alpha", "name": "Team Alpha", "capacity": 1, "available": []}
  ],
  "tasks": [
    {
      "id": "t1",
      "name": "Site survey",
      "duration_minutes": 120,
      "depends_on": [],
      "requires": [],
      "earliest_start": null,
      "deadline": null,
      "priority": 1
    }
  ]
}
```

Field notes: `capacity` is how many tasks a resource can run at once. An empty
`available` list means available for the whole horizon. An empty `requires`
list means any resource is eligible. Timestamps are ISO-8601 with no timezone
suffix — do not mix zones within one plan.

The model is expected to return:

```json
{
  "session": "example-001",
  "assignments": [
    {"task_id": "t1", "resource_id": "alpha",
     "start": "2026-08-11T08:00:00", "end": "2026-08-11T10:00:00"}
  ],
  "unscheduled": [{"task_id": "t9", "reason": "no window left"}],
  "rationale": "short explanation"
}
```

## What gets checked

Structural validation runs first: types, required fields, parseable timestamps,
intervals that end after they start. Then hard constraints:

Every task is scheduled exactly once, or explicitly listed as unscheduled with
a reason. Every task and resource id actually exists in the plan. Each block
lasts exactly the task's stated duration. No task starts before something it
depends on has finished. No resource runs more concurrent work than its
capacity allows. Work stays inside declared availability windows and inside the
plan horizon. Tasks respect their earliest-start and deadline. Start times
landing off the time grid are flagged as warnings rather than errors.

Plans are also checked for impossibility before a model ever sees them:
dependency cycles, tasks longer than the horizon, deadlines at or before their
own earliest start, and references to ids that do not exist.

## What a run folder holds

```
runs/20260811-084500-example-001/
  plan.json       the exact plan used (runs stay reproducible)
  packet.md       what was sent to the model
  output.raw.md   what came back, verbatim
  schedule.json   the parsed schedule
  summary.json    makespan, counts, per-resource utilization
  schedule.csv    spreadsheet export
  issues.json     every error and warning found
```

`runs/index.jsonl` is an append-only JSON Lines log — one line per stage and
ingest event, never rewritten. Run folders can be deleted without losing the
history of what happened.

## Layout

```
mitss/
  model.py        dataclasses for plans and schedules
  validate.py     structural validation (shape and types)
  constraints.py  hard-constraint checking (domain rules)
  capture.py      pulls JSON out of whatever the model returned
  packet.py       builds the prompt packet
  render.py       table, CSV, and ASCII timeline views
  diffing.py      run-to-run comparison
  runlog.py       run storage and the append-only index
  cli.py          command line interface
inputs/           plans you write
runs/             one folder per run (gitignored)
tests/            unit tests
```

## Tests

```bash
python -m unittest discover tests
```

42 tests covering validation, every constraint class, output capture from messy
replies, diffing, rendering, and storage.

## Design notes

The core model is domain-agnostic on purpose: tasks with durations,
dependencies, and eligibility, placed onto resources with capacity and
availability. Shift rosters, mission timelines, and asset booking all express in
those primitives, so pinning a domain later is a layer rather than a rewrite.

Validation returns lists of issues instead of raising, so one pass reports every
problem rather than the first one. Errors mean illegal; warnings mean legal but
suspect. See `DECISIONS.md` for the full decision log.
